<objective>
Generate the seed data script, perform manual schema push via Supabase SQL Editor, and create a script to verify the deployment.
</objective>

<threat_model>
- Assets at risk: Database data integrity
- Threat actors: Application developers / DB admins
- Attack vectors: Unintended destructive seed script execution in production
- Mitigations applied: Seed script uses `ON CONFLICT DO NOTHING`/`UPDATE` to be idempotent. Execution is flagged as manual (`autonomous: false`) to require human validation before applying to Supabase SQL editor.
</threat_model>

<title>Create seed data SQL file</title>
<read_first>
- .planning/phases/01-database-foundation-auth/01-PATTERNS.md (for seed data requirements and JSONB schemas)
</read_first>
<action>
Create file `supabase/migrations/003_seed_data.sql`.

Write the SQL to:
1. Seed Vendors: Cisco, Fortinet, Juniper, Palo Alto, MikroTik, Aruba / HPE, Huawei.
2. Seed Device Types: Switch, Router, Firewall, AP/WLC.
3. Seed Categories: interface-port, vlan, routing, switching, security-acl, system-mgmt, aaa-user, monitoring-troubleshooting.
4. Seed Canonical Actions: e.g. vlan.create, vlan.port_trunk, route.static_add, interface.ip_set, system.config_save.
5. Seed Commands: Write an anonymous PL/pgSQL block (`DO $$ ... END $$;`) to insert 50-70 commands covering all vendors and mapping to the canonical actions and device types. Include complete JSONB schemas for `parameters`, `examples`, and `warnings`.

Use the patterns and code snippets from section 2.3 of PATTERNS.md. Ensure all tables are populated using `ON CONFLICT` constraints for idempotency.
</action>
